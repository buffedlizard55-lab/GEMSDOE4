0. The whole submission in five commands

No training, no GPU, no DrivenData credentials needed for the repository side. This is the path that was re-executed in the development sandbox; the validator output it produces is committed at data/evidence/combined/validation.log.

git pull                                     # get the sha256-pinned raster bridge
python scripts/assemble_data_bridge.py       # verify + place data/training_features.tif, labels.tif, sample_submission.tif
python scripts/prepare_data.py               # pre-flight: grid, CRS, resolution, band tags
python scripts/validate_submission.py \
    --pred data/evidence/combined/submission.tif \
    --sample data/sample_submission.tif --train data/training_features.tif
# -> "✅ Validation PASSED - Ready for submission!"

Then upload data/evidence/combined/submission.tif at https://www.drivendata.org/competitions/306/competition-doe-gems/submissions/ (account + enrollment required — the one step this repository cannot do for you, see §8).

  1. Create / sign in to a DrivenData account and open https://www.drivendata.org/competitions/306/competition-doe-gems/.
  2. Click Compete! and accept the competition rules and restrictions (the rules are the PDF at https://docs.nlr.gov/docs/fy26osti/96647.pdf, mirrored on HeroX resource 2274).
  3. Download the data from the data tab — this needs the account you just created; the repository does not need it, because the same three rasters are committed as a sha256-pinned bridge under data/bridge/ (see §2).
Irregularity, flagged not hidden: the data tab's own mirrors are Dropbox links, and the file names there differ from the names the problem page uses (gems-geodawn-numerical-features.tif vs training_features.tif, existing_faults.tif vs labels.tif, example_submission.tif vs sample_submission.tif). scripts/assemble_data_bridge.py maps them by sha256, not by name, so the drift cannot silently substitute a file.

2. Put the official rasters in data/ and prove they are the official ones

data/ payloads are gitignored; data/bridge/ is committed in ≤ 90 MiB parts (GitHub rejects a 419 MB blob) with every part and the whole file pinned by sha256 in data/bridge/manifest.json. Reassembly verifies before it writes and aborts on any mismatch, so a corrupted or substituted raster cannot enter the pipeline quietly.

python scripts/assemble_data_bridge.py    # verify parts -> concatenate -> verify whole-file sha256 -> place canonical names
python scripts/prepare_data.py            # 3292x3730, 19 bands, EPSG:32611, 100 m, aligned bounds, band tags present

3a. Where the file can come from — including from this page

docs/how_to_submit.html §3 carries a generator that runs entirely in the reader's browser. scripts/build_submission_payload.py measured the artifact and wrote its pixel field into this site as a run-length stream (docs/submission_field.bin, 298,012 B for a 49,116,640 B float32 buffer); docs/geotiff_writer.js rebuilds a single-band float32 GeoTIFF on the grid the platform asks for, then re-reads its own bytes and refuses to hand over a download unless every pinned check agrees — and the command-line twin of it writes nothing at all when a check fails, so a refused build cannot be picked up later by mistake.

A browser cannot be driven by CI, so the same JavaScript is executed headlessly under node and judged by rasterio plus scripts/validate_submission.py: data/evidence/site_generator.json (verdict PASS, 10 measured steps). tests/test_site_generator.py re-runs it in every container the writer can emit (deflate and uncompressed strips, one-row strips, a single strip for the whole grid), because a raster proven only in the shape it was authored in is not proven.

The claim is about pixels, not bytes: deflate (zlib-wrapped, per strip — tag 8, as GDAL writes) against the artifact's lzw tiles. That is the deliberate boundary — what the platform enforces is grid, CRS, geotransform, single band, float32 and the [0,1] range, and each of those is an assertion in the page's own self-check table. A byte-identical copy would have been curl (route A), not a generator.

5. Upload it on DrivenData

  1. Open https://www.drivendata.org/competitions/306/competition-doe-gems/submissions/.
  2. Click Make new submission.
  3. Upload the validated .tif (route A: data/evidence/combined/submission.tif, 505,882 bytes · sha256 237f0063a440b2c6c4b822bcb0f74e5203586313b3b5ed6c5cabe70fa046f63f).
  4. In the narrative box paste the generative-AI disclosure from §6 (it is not counted in the word count, per the rules).
  5. Submit, then confirm on the public leaderboard that the submission parsed and scored. A file that fails ingestion shows no score.
This is the human-only step. This repository has no DrivenData credentials and the data tab redirects to a login, so no number in this repository has ever been confirmed by the official scorer. Everything here is measured against local surrogate populations; the public leaderboard is the first unbiased signal, and it needs a person with an account.

ConstraintWhat it means for us
3 submissions / weekA scarce resource: each upload is an experiment whose only read-out is the public split. The repository's surrogate measurements decide what to upload; the quota decides how often we can check.
One final selectionBefore the deadline, exactly one submission is marked final and is scored in both prize rounds — so the file that wins the public split is not automatically the right final choice.
No private-score knowledgeThe final selection is made blind on the private test set. This is why the repository pre-registers decision rules (docs/FIELD_SELECTION_RULE.md, data/evidence/emission_decision.json) instead of picking the best-looking local number.
Phase 2 re-scores the same fileAgainst the full expert-revised fault set. A file tuned to restate the training catalogue can only lose there; this is the argument for the emission policy that is measured on faults the labels do not contain.

Fold-restricted bootstraps also resample only 8–9 blocks, below the 12 the scorer itself requires before it calls an interval readable, so they are spread indicators, not confidence statements.

10. Irregularities flagged before you submit

#FindingHow it was establishedConsequence for the submission
1example_submission.tif is bit-identical to the labels raster, although the problem page describes the sample submission as predicting total fault absence. sha256 equality + pixel comparison, data/evidence/transfer_analysis.json Do not use the sample as a "no fault" baseline; use it only as the grid/CRS template (which is what scripts/validate_submission.py does).
2File-name drift between the problem page, the reference solution and the data tab's mirrors. data/bridge/manifest.json maps mirror name → canonical name by sha256 Handled; placement is by checksum, so a name cannot substitute a file.
3The 1 m DEM links file is a scan with no text layer; the competition JSON inside it contains duplicate rows and path/filename project mismatches. three extractors + OCR, then every tile URL checked against the USGS bucket (scripts/download_dem_tiles.py --complete-listing) DEM derivatives are still unused (external_dem_path: null); the canonical tile list is enumerable without the PDF.
4Submission cadence: an earlier project instruction said 2 per 7 days, the rules PDF says three per week. verbatim quote weekly_limit in data/evidence/rules_quotes.json Plan on 3/week (the official document wins) and check the number the platform shows at submission time.
5The cross-catalogue transfer measurement refused itself: QFaults and the training labels are the same lines (60,938 of 60,939 in-footprint QFaults px already within R = 3 px of a label). data/evidence/xcat/transfer_report.json, measured on a runner No free second Quaternary catalogue is independent of these labels, so external-catalogue signal is limited to SGMC — and §9 shows what that buys.
6The two official-format files disagree about the NODATA tag: sample_submission.tif declares NODATA=nan, the shipped artifact declares none, and both read as NaN outside the footprint. rasterio profiles of both files, compared by scripts/check_site_generator.py (step "NODATA tag: artifact vs the official template") and recorded in data/evidence/site_generator.json Declare NODATA=nan, like the template — which is what the in-browser generator does. It changes no pixel and no score, but a check that inspects tags rather than values could read an absent NODATA differently.
7"or a .zip file containing a single GeoTIFF" is a sentence of the platform's submit dialog, not of the rules PDF — §3.2 says a single GeoTIFF. the dialog sits behind a login this sandbox cannot reach, so the sentence is transcribed by the team; a full-text search of the extracted rules PDF for "zip" returns nothing, so it is recorded as an unverified-source claim rather than promoted to a rule Both containers are offered (scripts/package_submission.py writes the stored single-member zip the dialog describes and verifies it reads back). When in doubt upload the .tif: the rules wording is the half that can be verified from here.
